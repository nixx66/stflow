# STFlow 工业级代码重构规格

## 目标

在不改变页面 UI、交互、路由、接口协议和业务行为的前提下，重构全部 TypeScript、TSX 与相关服务端代码。结果应更接近长期维护的真实产品代码：命名直接、控制流清晰、抽象有业务价值、错误处理可追踪、文件职责明确。

## 不变量

- 保持所有公开路由、查询参数和 URL 结构不变。
- 保持 API 请求与响应字段、HTTP 状态码和持久化格式不变。
- 保持 LocalStorage 键名、发票状态、钱包角色、支付模式与回执数据不变。
- 保持可见文案、DOM 层级、CSS 类名、图片、动画和响应式行为不变。
- 保持现有公开导出；只有在确认仓库内没有外部消费者时，才允许删除未使用导出。
- 不引入新的运行时依赖，不更换框架、状态方案或样式方案。

## 重构顺序

### 1. 领域与基础设施

范围：`lib/`、`types/`。

- 合并重复的状态判断、地址比较、序列化与格式化逻辑。
- 删除未来功能占位代码和无调用路径的辅助函数。
- 缩短刻板命名，但保留领域含义，例如使用 `invoice`、`payer`、`receipt`、`txHash`。
- 用提前返回替代深层嵌套。
- 保留浏览器存储不可用、损坏服务端存储和钱包扩展差异等真实边界处理。

### 2. API 与数据访问

范围：`app/api/`、`lib/invoiceServerClient.ts`、`lib/serverInvoiceStore.ts`、`lib/supabase.ts`。

- 统一 JSON 解析、参数校验和错误响应路径。
- 移除只吞错或只输出控制台日志的捕获。
- 对预期错误返回稳定的 HTTP 响应；未知错误继续向框架错误边界传播或记录后抛出。
- 文件存储恢复逻辑保留损坏文件隔离行为。

### 3. Hooks 与支付流程

范围：`hooks/`、`lib/paymentMode.ts`、`lib/usdc.ts`、钱包组件。

- 减少重复状态，派生值不保存为独立状态。
- 保持钱包连接、支付授权、交易等待和模拟模式行为不变。
- 删除仅描述未来实现步骤的注释；只保留链上精度、钱包限制和降级策略的原因说明。
- 异步错误使用明确的 `Error` 实例和可消费状态，不使用无效 `console.log`。

### 4. 业务组件

范围：发票、付款、回执、控制台组件。

- 拆分超过单一职责的大组件，优先处理 `InvoiceForm.tsx`、`PaymentPanel.tsx`、控制台发票页面。
- 抽取只在两个以上调用点存在且语义稳定的逻辑。
- 避免通用 `utils`、无意义接口层和只转发参数的包装组件。
- 表单字段、按钮、可访问性属性和提交顺序保持不变。

### 5. 页面与展示组件

范围：`app/` 页面、`components/home/`、Dashboard 与 Resources。

- 将静态配置移至文件顶部或相邻模块，减少 JSX 内重复结构。
- 保持可见输出、布局和样式完全一致。
- 不为纯展示代码引入额外状态、Context 或客户端边界。
- 保留确有视觉用途的动画组件，不以“简化”为名改变动画效果。

## 注释规范

- 删除解释语句含义或重复函数名的注释。
- 保留说明浏览器、钱包、链上精度、文件损坏恢复和兼容性取舍的原因注释。
- 不保留 TODO 式未来实现清单；未实现能力通过文档或 issue 管理。
- 不添加章节式、教程式或总结式注释。

## 命名规范

- 变量和函数优先使用 1 至 3 个有领域意义的单词。
- 事件处理器使用动作名，例如 `submit`、`pay`、`connect`；仅在同一作用域有歧义时加对象名。
- 布尔值使用 `is`、`has`、`can` 前缀。
- 避免 `data`、`result`、`item` 等无上下文名称，但短小 map 回调中的局部 `item` 除外。
- 不通过缩写牺牲领域可读性；`id`、`url`、`api`、`tx` 等通用缩写允许使用。

## 错误处理

- 预期的用户输入错误返回可操作信息。
- 可恢复的浏览器能力错误采用明确降级路径。
- 服务端数据损坏先隔离原文件，再恢复为空存储。
- 未知错误不静默吞掉；由调用方状态、框架错误边界或结构化服务端日志处理。
- 禁止只有 `console.log`、`console.warn` 或 `console.error` 的 catch。
- 仅在 best-effort 清理、广播和非关键缓存失效场景允许显式忽略失败。

## 测试与验收

### 自动化基线

- 现有 41 项测试必须持续通过。
- 为拆出的纯函数、边界处理和修复的缺陷先添加失败测试。
- `tsc --noEmit` 必须无错误。
- Next.js 生产构建必须成功生成全部现有路由。

### 行为验收

- 发票创建、共享链接、付款、回执和控制台数据流保持一致。
- API 创建、读取、更新和损坏存储恢复行为保持一致。
- 首页 Dashboard 导航继续指向 `/dashboard`。
- Mock 与 Live 支付模式的可用性判断保持一致。

### 视觉验收

- 对首页、Dashboard、发票创建、付款和回执页面做改动前后同视口截图对比。
- 不允许出现布局位移、字体变化、颜色变化、内容缺失或交互控件变化。

## 提交策略

- 每一层形成独立提交，避免把业务逻辑、UI 和基础设施改动混在一个提交中。
- 每次提交前运行受影响测试；阶段结束运行完整测试与类型检查。
- 最终提交前运行生产构建与视觉回归。

## 非目标

- 不新增功能、页面、API 或设计。
- 不改变数据库或部署架构。
- 不升级依赖，不切换测试框架。
- 不追求任意代码指标，也不为了减少行数压缩可读性。
- 不把项目重写成新的架构范式。
